## What survived, ranked (users reached times cost)

1. **B3** watch app and complication always show 0 and "Check in on your iPhone". Every watch user, always.
2. **B2** iPhone widget never shows a practice score and lags the streak after a practice. Every widget user on the practice loop, daily.
3. **B1** daily practice reminder still fires after the practice is done (one title in six says the practice is waiting). AirPods users who practise before the reminder time, daily, low cost.
4. **B4** "Safety net" announced on day one. Every new user, once.
5. **B6** streak reads 0 for one day on a run that is still savable. Rare, could cost the run.
6. **B9** "Next reminder later today · 0 more today" with permission denied. Small, cosmetic.
7. **B10** stale "Notifications are off." banner after allowing. Small, cosmetic.
8. **B7** wide 15-minute windows cut at 20:45 without telling the user. Very few.
9. **B8** first spent save returns the next day. Harmless, a product decision.

B5 stays UNVERIFIED and, if real, self-heals on the next foreground.

Ranking changes from the audit: B3 moves above B2 and B1 (an always-wrong headline number beats an occasional extra reminder); B1 drops from 1 to 3 because the cited Settings copy describes the shipped behaviour and only one rotating title is false; B6's cost is moderate, not high.

## Product calls

- P1 (Practice again adds level passes): agree it is a product call. The anti-farm comment covers custom lengths only (`PracticeSessionView.swift:140-142`); repeat full-length passes are real practice.
- P2 (reminder tap opens the default mode): documented (`GoalSettings.swift:22-26`). Agree, not a bug.
- P3 (re-subscribing resumes all-day monitoring): agree. The user consented when they first turned it on (`SettingsView.swift:336-347`), and `reconcileMonitoring` resumes it (`App.swift:209-216`). Low.
- P4 (store recovery leaves setup flags set): agree on the facts (`DataService.swift:92-105`, flags in `UserDefaults`). This is a real state inconsistency rather than taste, but it needs a non-transient store failure, so it stays rare. Worth fixing alongside any recovery work.
- P5, P6: not settled by the audit or this review (SwiftUI presentation and missing-tag selection behaviour). Each needs one device or simulator run.
- P7 (check-in credits the streak for AirPods users): documented in the check-in copy. Agree, not a bug.
- P8 (pending purchase shows no message in two sheets): agree, low.

Missed in scope: the B5 family also covers turning check-in reminders off while an "on" pass is still adding: `cancelAllReminders` (`ReminderScheduler.swift:45-47`) can run before the earlier pass's remaining adds, leaving slots pending until the next foreground. Same timing caveat and self-heal as B5. No serious state bug outside the audit's list turned up in the files read.

## Method changes that would have prevented the errors

1. Read the cited promise in full and check the project's own docs before ranking. B1 was ranked first on one of six rotating titles while the cited Settings line and AGENTS.md describe the shipped behaviour.
2. Compute each route with real numbers. B5's route (Start 6, End 23, step End down) gives identical 60-slot sets because of the cap, so the first taps cannot leave stale slots.
3. Reach hand-built states through the real service calls. B6's state is reachable, but from a fresh install it takes 4 misses, not 3, because of B8.
4. Give one mechanism one id. The watch widget sits in both B2 and B3; it belongs to B3.
5. Count self-healing paths in impact. B5 is undone by the next foreground reschedule.
6. Split "code path" into "code leaves no doubt" and "timing or platform dependent". Only the second needs a device; B1, B7, B9 and B10 were provable by reading, B5 was not.
7. Weigh always-wrong displays above occasional notifications when ranking reach times cost.
